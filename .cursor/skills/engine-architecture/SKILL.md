# Tiny3D 引擎架构分析与设计

## 目标

用代码回答「现在到底怎么分层、谁调用谁」，再决定要不要改、怎么改。

三种任务：

| 类型 | 何时 | 产出 |
|------|------|------|
| **现状分析** | 摸清某模块真实结构 | 类型职责、数据流、扩展点 |
| **设计对照** | 已有 `doc/todo` 或架构文档 | 设计声称 vs 代码实际的差距表 |
| **新设计** | 要加能力或重构 | 基于现状的可落地方案（不写实现代码） |

未指定类型时先做现状分析。

## 硬性约束（必守）

1. **先读实现，再下结论**。未读相关 `.h` / `.cpp`（或 `.mm`）与调用链之前，禁止写「架构是…」或出方案。
2. **文档是假说，代码是真相**。`doc/Tiny3D-Architecture.md` 与 `doc/todo/` 可能过时（例如已删的后端、已改的类名）。与实现冲突时以实现为准，并在对照表里标出来。
3. **禁止臆造**。不得凭类名、目录名补生命周期、线程模型、错误码或插件约定。看不清就写「待证实」。
4. **新设计必须长在现状上**。每个新增类型/接口都要写清：复用谁、避开谁、为什么不另起炉灶。没有文件级依据的方案不算完成。
5. **只写 markdown，不改源码**。允许创建或更新的文件仅限 `doc/todo/**/*.md`。禁止改 `source/`、CMake、插件、资源、测试，以及 `doc/todo` 以外的任何路径。接口草案用「建议实现」标注，不当成已落地代码。落地实现走 `general-manager` → `code-implementer`，本 skill 不写业务代码。

## 工作流

```
Architecture Progress:
- [ ] 1. 确认范围与任务类型
- [ ] 2. 搜已有设计文档（当假说）
- [ ] 3. 按入口定位头文件与实现
- [ ] 4. 读调用链 / 插件实现 / 生命周期
- [ ] 5. 写现状（实际架构）
- [ ] 6. 对照或设计（若任务需要）
- [ ] 7. 标风险与待证实
- [ ] 8. 设计稿落入 `doc/todo/**/*.md`（仅此目录）
```

### 1. 确认范围

用户指定其一即可：主题、模块目录、已有设计文档、关键类型名。范围过大（例如「整个渲染」）先拆成 RHI / Render / 材质 / 后端插件，分批推进。

### 2. 搜文档（先读，不当真理）

按这个顺序找，记下路径与日期感（是否像施工蓝图、是否已部分落地）：

- `doc/Tiny3D-Architecture.md` — 分层总览，**须用代码复核**
- `doc/*Architecture*.md`、`doc/refs/` — 后端与 API 对照
- `doc/todo/` — 进行中的设计与分步计划
- `.cursor/rules/` — 已沉淀的局部设计约定

文档结论一律标成「文档声称」，进入步骤 3 后才能升格为「实际」。

### 3. 读代码（设计之前必须完成）

默认配对：

| 头文件 | 实现 |
|--------|------|
| `source/<Mod>/Include/.../T3DXxx.h` | `source/<Mod>/Source/.../T3DXxx.cpp` |
| 插件 / 编辑器同理；Apple 后端可能是 `.mm` | 同名源文件优先，找不到再搜符号定义 |

阅读顺序：

1. **入口与门面**：单例、Manager、`Agent` 持有关系、对外头文件。
2. **核心类型**：基类、工厂、插件接口、关键 `override`。
3. **实现**：控制流、失败路径、资源生命周期、谁创建/谁释放。
4. **调用方**：谁在每帧、加载、序列化、编辑器里用它。
5. **平台分叉**：`#if T3D_OS_*`、Runtime vs Editor（`Core/Runtime` vs `Core/Editor`）、插件 Window/Console/Runtime 变体。

模块入口见 [modules.md](modules.md)。索引与实现不符时，以实现和 `CMakeLists.txt` 为准。

### 4. 写现状

至少回答：

- 边界：这个子系统对上对下暴露什么，不负责什么
- 关键类型与文件（路径 + 一句话）
- 数据流 / 帧循环中的位置（能画 mermaid 就画）
- 已有扩展点（虚接口、插件、工厂、事件、RTTR）
- 与相邻模块的真实依赖（include 与链接，不是文档里的愿望）

### 5. 对照或新设计

**设计对照**：表格三列——文档/设计声称 | 代码实际 | 差距（缺失 / 已变 / 已废弃 / 部分落地）。

**新设计**：

- 先用 3～5 条列出「必须遵守的现状约束」
- 再写目标、非目标、总体结构、接口草案、分阶段落地
- 接口草案标注「建议」，并链到现有参考实现位置
- 风格对齐仓库：GameObject + Component、RTTR（`TCLASS`/`TPROPERTY`）、插件 Runtime/Editor 双版本、Platform 的 Interface → Wrapper → Factory
- 详细编码规范见 `doc/Tiny3D-Coding-Style.md`，本 skill 不重复

## 输出模板

### 现状分析 / 设计对照 / 新设计（统一用这个骨架）

```markdown
## 架构结论
- 范围：
- 任务类型：
- 已读文档：
- 已读关键代码：
  - `path` — 职责
- 现状（实际架构）：
- 设计对照：（本次不做则写「本次不做」）
- 推荐方案：（本次不做则写「本次不做」）
- 风险与兼容性：
- 待证实：
- 已落盘：
```

新设计的「推荐方案」建议再拆：

1. 现状约束（来自代码）
2. 目标 / 非目标
3. 结构与数据流（mermaid）
4. 新增或改动的类型（文件建议路径 + 职责）
5. 分步落地（依赖写清，可并行的标出来）
6. 明确不改的部分

### 6. 落盘（只写 markdown）

| 任务 | 是否落盘 | 路径 |
|------|----------|------|
| **新设计** | 必须 | `doc/todo/<Topic>-Design-todo.md` |
| **设计对照** | 必须 | 用户已指定文档则更新该 `doc/todo/*.md`；否则新建 `doc/todo/<Topic>-Design-todo.md`，把差距写进「现状分析」 |
| **现状分析** | 用户要求，或结论需要后续设计接着用 | `doc/todo/<Topic>-Status-todo.md` |

规则：

- 只 `Write` / 编辑 `doc/todo/` 下已有或新建的 `.md`。目录不存在就只建 `doc/todo`，不要建别的树。
- 已有同主题文件先打开再改，避免并行一份内容重复的稿。
- 正文用中文；代码片段标「建议实现」，并链到现有参考文件。范例结构：`doc/todo/Inspector-Panel-Implementation-todo.md`。
- 落盘后在回报的「已落盘」里写完整相对路径。

禁止：改 `.h` / `.cpp` / `.mm` / `.cmake` / `CMakeLists.txt`、插件、资源、`.cursor/`、`doc/` 下非 `todo` 的文件。

## 质量检查

- [ ] 结论都能指到具体文件，不是目录级空话
- [ ] 文档与代码冲突处已点名，没有「各说各话」
- [ ] 待证实与已证实分开
- [ ] 新方案写了复用点，没有无故新造平行体系
- [ ] 没有改源码或非 `doc/todo` 文件；落盘的只有 `.md`
- [ ] 没有把方案写成已落地代码
